--------------------------------------------------------------------------------
2. Two defects found only by opening a real stream
--------------------------------------------------------------------------------
Both are recorded because `implementation/evidence/capture.txt` (16 lines) had
ever done enumeration, never `GetMixFormat` + `Initialize`. The brief's gotcha
list said "accept tag 65534"; it did not say where the sub-format lives, and the
first implementation got that wrong in two different ways.

2a. Sub-format read past the end of the header copy.
    First run, `flux capture start --tap loopback --secs 8` -> exit 1:
      FluxError { code: AudioDeviceLost, subsystem: "capture",
        message: "unsupported wire format: tag 65534, 32 bits, 2 channels — only
        float32 (tag 3 or extensible float) and 16-bit PCM (tag 1 or extensible
        PCM) are decoded" }
    Cause: `classify()` took the 18-byte `WAVEFORMATEX` *copy* and then read a
    `WAVEFORMATEXTENSIBLE` out of it, i.e. 22 bytes past a value that was never
    that long. The `SubFormat` it compared was stack noise, so a perfectly normal
    float32 mix format was refused.
    Fix: the extension is copied from the engine's own allocation, before
    `CoTaskMemFree`, and `classify(wave, ext)` refuses tag 65534 whose extension
    is not present instead of guessing it.
    Proof after the fix: classification accepted the endpoint —
    `wire: 48000 Hz, 2 ch, 32 bit, tag 65534 (float32), extensible=true`.

2b. `Initialize` handed a header that promised 22 bytes it did not have.
    Second run, same command -> exit 1:
      FluxError { code: AudioDeviceLost, subsystem: "capture",
        message: "Initialize failed on {0.0.0.00000000}.{8d8bb8ef-...}
        (2 channels, 48000 Hz, tag 65534, 10 ms buffer): The parameter is
        incorrect. (0x80070057)" }
    Cause: `addr_of!(wave)` — the 18-byte header with `cbSize` 22 — is not a
    valid format block. Shared mode wants the whole `WAVEFORMATEXTENSIBLE`.
    Fix: pass a pointer to the full extensible copy when there is one, and to the
    plain header when there is not.
    Proof after the fix: sections 3 and 4 below opened streams.

2c. `flux capture stop` did not end a `capture start --secs N` run.
    Measured before the fix (SSL 2 mic run, `--secs 20`, stopped at 4.6 s):
      ran 20142 ms / packets=478 frames=229440 / valid=false stalledMs=15212
    The capture thread saw the request and stopped the stream; the CLI slept its
    whole budget anyway and published 15 s of watchdog, while its own note
    claimed the run "exits within its poll interval".
    Two causes, both fixed: the status writer re-emitted `stopRequested: false`
    every 250 ms (a race against the 100 ms reader), and `measure()` used one
    unconditional `sleep(secs)`.
    Measured after the fix, section 5: `ran 8426 ms` for `--secs 20`.

one window per ~10.7 ms hop, and `windows` advanced without `overflowEvents`.

peak 0.0417 -> 0.1658 is x3.981; 10^(12/20) is 3.981. The trim is a stated
user gain applied to the captured buffer, and nothing adjusted it by itself:
this is the refusal of auto-trim that the brief asked for, with the reason
(`volume=0.2` arriving at `peak=0.0083`) now reproducible on this host.

  flux capture status while it ran -> exit 0
    pid=54052 stopRequested=false compiled=true running=true tap=loopback
    rate=0.0 windows=0 packets=0 frames=0 valid=false stalledMs=8033 elapsedMs=8033

  flux capture stop -> exit 0
    stop requested: true
    note: the running capture stops its stream and ends its wait within 100 ms;
          `flux capture status` keeps the last reading it published.

Three things this pins: an idle loopback tap produces *no packets at all* on this
host, so the watchdog is the only thing standing between "quiet room" and a
plausible-looking all-zero measurement; `valid=false` with `stalledMs` surfaced
instead; and the run ended 11.6 s before its `--secs` ceiling once asked.
Note that WASAPI reported silence as absence, not as silent frames: `silent=0`
and `packets=0`, which is why counting packets (not `SILENT` flags) is the
stall signal.

    pid=58404 stopRequested=false compiled=true running=true tap=mic
    endpoint=Input (7- SSL 2 USB Audio Device) id={0.0.1.00000000}.{2f61d159-...}
    wire: 48000 Hz, 2 ch, 32 bit, tag 65534 (float32), extensible=true
    buffer=10 ms ring=100 ms (holds 682.7 ms) trim=+0.0 dB
    rate=46387.4 windows=415 onsets=0 packets=443 frames=212640 silent=0
    level: peak=0.0000 rms=0.0000 centroid=180 Hz
    valid=true stalledMs=1 elapsedMs=4584
  flux capture stop -> exit 0

The SSL 2 opened in WASAPI *shared* mode at 48 kHz float32 while its ASIO client
was not running, and delivered ~96 packets/s. `valid=true stalledMs=1` with
`peak=0.0000` is the honest reading of a live, open microphone in a quiet room:
packets arrive, so this is a measurement of silence, not a lost device — the
distinction the watchdog exists to make. `centroid=180 Hz` on a zero-signal
buffer is analyser noise and is reported as such, not as a feature.
