--------------------------------------------------------------------------------
What this proves, measured on the current tree
--------------------------------------------------------------------------------
- The NDI runtime loads and `NDIlib_initialize` succeeds on this host, and a discovery
  query runs and returns a list. Today that list contains no third-party sender, so the
  2026-11-09 record of "5 live sources" (evidence/ndi-discovery-live.txt) was an
  environment state - Premiere, the NVIDIA sender and the Test Patterns app were open -
  not a capability, and it does not reproduce unattended.
- Send and receive reproduce BOTH ways: same-process loopback (921,600 bytes = 640*360*4
  back with non-zero content) and cross-process (`ndi-send` -> `ndi-recv` into a PNG whose
  sampled pixels are the sent gradient). So the 2026-11-09 cross-process claim stands; it
  is no longer the only evidence of it.
- The harness step formerly named `ndi-discovery` runs `cargo test -p flux-integrations
  --features ndi ndi::`, which selects exactly two tests
  (`runtime_loads_and_initializes`, `discovery_returns_state_without_crash`) and asserts
  nothing more. Both return early when the runtime cannot be dlopened, so on a machine
  without NDI they used to record ok:true for zero assertions. verify.ps1 now probes the
  same candidate list ndi.rs walks and writes blocked_external when it finds no DLL, under
  the honest name `ndi-runtime-loads`. The `ndi::` filter does NOT select
  `ndi_io::tests::shim_loads_and_initializes`, which is the only harness test touching the
  shim.
- The fix that made the loopback work: `cmd_ndi_loopback` used to hand the sender's own
  name to `ndi_shim_recv_create`, which passes it to `NDIlib_recv_create_v3` as
  `p_ndi_name`. NDI advertises "{machine} ({sender})", so the subscription could never
  match; the loop timed out after 40 x 150 ms and the command still exited 0. Every run of
  that command before 2026-11-15 printed a failure and reported success to whatever watched
  the exit code. `cmd_ndi_recv` never had the bug - it subscribes to the discovered name -
  which is what located it.

- No Flux engine frame ever crossed this path. Both patterns are generated in

- Interoperability with a named third-party consumer (Resolume, TouchDesigner, an NDI

  evidence about a 6-day-old binary that happens to still be on disk.
