--------------------------------------------------------------------------------
0. WHY THIS FILE EXISTS
--------------------------------------------------------------------------------
Every NDI measurement in this repository before 2026-11-18 put a synthetic gradient on
the wire. `crates/app/src/main.rs` built it there (`fill_gradient`: R = (x*255/w + t/8)
% 256, G = y*255/h, B = 128, A = 255) and `AT060`'s generated blocker said, accurately,
"there is no wgpu->NDI path so a Flux render is never what is sent".

`flux ndi-loopback` and `flux ndi-send` now build a `Project`
(`samples::demo_generator_project("gen.plasma", &["fx.bloom"], 4)`) and render it through
`export::PreviewRenderer` — main.rs:520 in the loopback, main.rs:734 with the per-frame
`render_rgba_at` call at :745 in the sender — and hand those bytes to `NdiSender::send`.
`flux spout-send-dx` still sends `fill_gradient` (called at main.rs:891, the function at
:953), which is why that row stays open.

The command does not claim byte-exactness. It cannot: the transport is lossy, and the
first draft of this measurement asked for equality and came back with a maximum delta of
17. What the command asserts instead is written out below, and the residual is printed
rather than absorbed into a tolerance.

3. A defect this found in `flux ndi-send`, and the fix
--------------------------------------------------------------------------------
Before the runtime load was added, `ndi-send` could not start on this host at all:

  flux: FluxError { code: SdkMissing, subsystem: "ndi",
          message: "ndi-send: ndi_shim.dll not found (build apps/ndi-bridge)" }   exit 1

The DLL is there (24,064 bytes). `NdiShim::load` walks
`flux_platform::layout::candidates`, whose `bases()` ends in `PathBuf::from(".")`, so the
candidate that matches is the RELATIVE path `./apps/ndi-bridge/ndi_shim.dll`, and
`LOAD_WITH_ALTERED_SEARCH_PATH` on a relative `lpFileName` is documented as undefined
behaviour: the shim's own import `Processing.NDI.Lib.x64.dll` is not resolved from the
shim's directory. `cmd_ndi_loopback` and `cmd_ndi_recv` escape this only because they load
the RUNTIME first, by an absolute path, so the module is already in the process when the
shim is mapped and the loader satisfies the import by base name — that order is a comment
at main.rs:446-448 and was never a rule any command had to follow. Setting
`FLUX_NDI_SHIM` to the absolute shim path did not help on that same pre-fix binary: exit 1,
same message. (That probe is stated of the pre-fix build only. Re-running it against the
fixed build answers a different question — the fix loads the runtime by absolute path
before the shim is even asked for, so the variable no longer routes around anything.)

`cmd_ndi_send` now loads and initialises the runtime before the shim, the same order the
other two use (main.rs:687-700, the shim load following at :701).
`ndi_commands_load_the_runtime_before_the_shim` (main.rs:2708) scans the source for that
order in all three commands, and it has been seen red twice, because the first red was
taken on bytes the tree no longer has.

4. What this file does NOT show
--------------------------------------------------------------------------------
- It is not byte-exact and it is not claimed as one. Max R17 G6 B11 A0 over 921600 bytes.
- No consumer that is not Flux received anything here. Both processes in section 2 are
  Flux; the peer is Flux's own receiver, as it has been in every NDI run this repository
  has recorded. Resolume Arena was not taken as the independent peer for this tranche.
- Nothing past same-machine loopback: no second NIC, no Wi-Fi, no VLAN, no bandwidth
  collapse, no reconnect.
- The running app's output is not what goes out. `trait LiveSink`
  (crates/integrations/src/live.rs:36) still has no implementor; what crosses is a CLI's
  own one-shot render of a document, made for the purpose of being sent.
- 640x360 is what these two commands choose for the fixture. A project passed as
  `ndi-send <name> <secs> <path>` broadcasts at its own canvas size; that path is
  exercised by nothing in this file.
- `ndi_shim.dll` and `Processing.NDI.Lib.x64.dll` in apps/ndi-bridge are gitignored
  artifacts of this machine; a fresh clone cannot rebuild either without the SDK
  (`build_shim.bat:7` reads the headers out of this machine's cargo registry).
- release counts, line stride and timestamps are still unmeasured, which is the other
  half of what AT060's blocker lists.

6. The summary line printed a drift claim it does not measure
--------------------------------------------------------------------------------
Section 5 quotes run E's two per-phase lines, and one of them says "at t=2s 60 frame(s)
back … 1 of them different from the first". The same run's last line said "the transport
returned 102 repeated frame(s) without a single byte of drift". Both sentences were
printed by one invocation of one command, and they contradict each other.

The cause was the string, not the measurement: that clause was a literal in the
`println!` at `crates/app/src/main.rs:645-660`, written when every run so far had happened
to return zero variants, while the count the command actually holds (`PumpOutcome::variants`,
main.rs:1861) was never interpolated. So the command asserted a property of the transport
from a value it had decided not to read — the same class AGENTS.md names for a CLI that
prints a failure and exits 0, with the verdict rather than the status being the thing that
lied. The struct's own doc comment had already said what a variant means ("one change is the
stale frame the previous phase left in the receiver"), so the number was not new: the
sentence printed was the one that had not caught up with it.

The fix prints the number: "the transport returned {} frame(s), {} of them differing from
the frame immediately before" (`o0.frames + o1.frames`, `o0.variants + o1.variants`). Two
lines longer, and that moved every line number in the file below the `println!` by +2, so
the citations into `cmd_ndi_send`, `cmd_ndi_recv`, `cmd_spout_send_dx`, `cmd_osc_listen`
and `capture_devices` across `docs/PERFORMANCE-READINESS.md`, `implementation/STATE.json`,
`implementation/DECISIONS.md`, `implementation/evidence/live-capture-2026-11-16.txt` and
`PLANNING/AUDIO-REACTIVE-LANE-PLAN.md` were re-resolved against the current bytes rather
than shifted by arithmetic — 30 sites, each checked by printing the line it lands on.
